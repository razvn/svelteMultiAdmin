Access rules

access is a list of rules. A rule matches people and adds grants. Every request, the portal merges the grants of all matching rules for the person. 

"access": [
	{
		"match": { "group": "platform-admins" },
		"grants": { "myadmin": true, "redisadmin": { "role": "admin" }, "userAdmin": true }
	},
	{ "match": { "group": "devs" }, "grants": { "redisadmin": { "role": "rw", "servers": ["Dev redis1"] } } },
	{ "match": { "email": "carol@example.com" }, "grants": { "myadmin": true } },
	{ "match": { "group": "*" }, "grants": { "redisadmin": { "role": "ro" } } }
]

Matching

Each rule has a match with exactly one of:

  • group: the person is in this group. "*" matches everyone.
  • user: the user name, exactly.
  • email: the email address, case-insensitively.

Grants

Grant Effect
"myadmin": true May open svelteMyAdmin. Access is all or nothing: the app connects with the server's configured MySQL account for everyone. Narrow it with the app's Kubernetes access checks if you use discovery.
"redisadmin": { "role": "ro" | "rw" | "admin", "servers": [...] } May open svelteRedisAdmin with that role. servers lists Redis server names (the name of each server in redisadmin.json); omit it for all servers. A name the app does not have grants nothing. The role is always sent to the app, so it never falls back to its "admin" default.
"userAdmin": true May manage local accounts on the Users page. Only effective with local authentication.

How rules combine

  • myadmin is granted if any matching rule grants it.
  • The Redis role is the highest of the matching rules (ro < rw < admin).
  • Redis servers are the union of the matching rules' lists. A rule with no servers means all of them and wins over any list. A matching rule with an empty list adds nothing.
  • Nothing matching means no access: the launcher says so and a direct link answers 403.

Rules are read when the portal starts. Group changes of a local user apply on their next click; for OIDC at their next sign-in; for trusted headers on the next request.

What the apps still decide

  • svelteRedisAdmin enforces the role on every destructive action, and answers 404 for servers outside the list.
  • Both apps run their own Kubernetes SubjectAccessReview checks for discovered servers, using the person's name and groups from the portal, when you configure authorize. See the apps' docs: svelteRedisAdmin, svelteMyAdmin.
