Authentication

Pick one mode in auth.type. Whatever the mode, the result is the same: a person with a user name, optional email and groups, which the access rules turn into grants.

`auth.type` Who signs in Session
local Accounts stored by the portal in usersFile Portal session cookie
oidc Any OpenID Connect provider Portal session cookie
trusted-header An SSO proxy in front of the portal None: the proxy's headers are read on every request

Local accounts

"auth": { "type": "local", "usersFile": "/data/users.json", "bootstrapAdmin": "admin" }
  • Accounts live in usersFile (JSON, written atomically with 0600 permissions). Passwords are hashed with scrypt. Usernames are lowercase letters, digits and . _ @ -.
  • The first start creates bootstrapAdmin with the password in MULTIADMIN_BOOTSTRAP_PASSWORD, in the groups of MULTIADMIN_BOOTSTRAP_GROUPS (default platform-admins). If the account does not exist and the variable is missing, the portal refuses to start and says so. Give that group userAdmin in an access rule, as the sample config does.
  • People with userAdmin manage accounts on the Users page: add, change groups or email, reset a password (leave the field empty to keep it), disable, delete. You cannot delete yourself.
  • Five failed sign-ins for a username within five minutes lock that username for the rest of the window. A wrong password and an unknown user take the same time.
  • A local user is read again on every request: disabling or regrouping takes effect on their next click.
  • Groups of local users are not passed to the apps as Kubernetes groups, so a local admin cannot create a user in a group like system:masters.

OpenID Connect

"auth": {
	"type": "oidc",
	"issuer": "https://idp.example.com",
	"clientId": "multiadmin",
	"clientSecretEnv": "OIDC_SECRET",
	"groupsClaim": "groups",
	"scopes": ["openid", "profile", "email"]
}
Key Meaning
issuer The provider's issuer URL. Its discovery document is fetched once.
clientId, clientSecret Your client. Prefer clientSecretEnv, the name of an environment variable holding the secret.
groupsClaim Claim with the person's groups, as a list or a comma-separated string. Default groups.
scopes Default openid profile email.
allowInsecureIssuer Allows an http:// issuer, for a local provider in development only. Default false.
  • Register <publicUrl>/auth/callback as the redirect URI at your provider.
  • The flow is the authorization code flow with PKCE (S256), state and nonce. Its state is kept in a short-lived, encrypted cookie and checked on the callback together with the ID token.
  • The user name is preferred_username, then email, then sub. An email is used only if the provider does not mark it unverified. A name with a comma, whitespace or control characters is rejected, and unsafe group names are dropped.
  • Groups are read when the person signs in. A group change at the provider applies at their next sign-in (at most sessionTtlSeconds later).
  • The groups also reach the apps as Kubernetes groups, for their access checks. The prefixes the apps use (authorize.userPrefix, groupsPrefix) must match your API server's --oidc-username-prefix and --oidc-groups-prefix.
  • Logging out ends the portal session but not the provider's own session.

Trusted headers behind an SSO proxy

"auth": {
	"type": "trusted-header",
	"userHeader": "x-auth-request-user",
	"emailHeader": "x-auth-request-email",
	"groupsHeader": "x-auth-request-groups",
	"trustedProxies": ["10.42.0.0/16"],
	"logoutUrl": "/oauth2/sign_out"
}

An SSO proxy (oauth2-proxy, an ingress auth-url, Pomerium…) authenticates the person against your identity provider and forwards who they are in headers. The portal reads them on every request, so when the proxy's session ends, access ends.

  • Only from trusted peers. The headers are honoured only when the direct TCP peer is one of trustedProxies (IPs or CIDR ranges, IPv4 or IPv6, required and non-empty). From any other address they are ignored, because anyone can send them.
  • The user header must hold a name with no comma (a comma means the header arrived twice), no whitespace and no control characters.
  • The three header names default to the x-auth-request-* headers of oauth2-proxy. emailHeader and groupsHeader may be null.
  • The proxy must cover all three hostnames (portal and both apps): the portal checks the identity on each of them. With oauth2-proxy, set its cookie on the parent domain.
  • logoutUrl is where "Log out" goes, usually the proxy's sign-out. Without it, the person lands on a page saying to sign in through the proxy.
  • Behind the proxy, the apps' audit logs record the real client address: the portal walks X-Forwarded-For from the right through the trusted proxies.
  • Do not set ADDRESS_HEADER on the portal in this mode: the check relies on the real TCP peer.
