Deployment

Build the image

The two apps are git submodules in vendor/. Fetch them, then build one image that holds the portal and both apps, each built from its own lockfile: 

git submodule update --init    # or: pnpm bundle:update (see "Updating the apps")
docker build -t multiadmin .
docker run -p 3000:3000 \
  -v ./multiadmin.json:/config/multiadmin.json \
  -v ./myadmin.json:/config/myadmin.json \
  -v ./redisadmin.json:/config/redisadmin.json \
  -v multiadmin-data:/data \
  -e MULTIADMIN_BOOTSTRAP_PASSWORD=change-me multiadmin

The image runs as a non-root user under tini, listens on 3000, and has a health check on /api/health.

Three hostnames

The portal and each app have their own hostname, so the apps need no changes to live under one address. Point three DNS names (for example admin.example.com, mysql.admin.example.com, redis.admin.example.com) at the same Service and Ingress; the portal tells them apart by Host. The three publicUrl values must be different. For local development, browsers resolve *.localhost to the loopback address: portal.localhost, myadmin.localhost, redisadmin.localhost.

Proxy headers

The portal derives its public origin from the x-forwarded-proto and x-forwarded-host headers of your ingress (PROTOCOL_HEADER and HOST_HEADER, already set in the image). Without them SvelteKit assumes https and refuses every form submission as cross-site. A browser does not send x-forwarded-proto by itself, so for plain http on your machine put a small proxy in front that adds x-forwarded-proto: http, or use https.

Do not set ADDRESS_HEADER on the portal. The identity checks rely on the real TCP peer.

Uploads

The portal accepts any body size and each app enforces its own limit. svelteMyAdmin's import page streams files, but its default limit is small: raise it with MULTIADMIN_MYADMIN_BODY_SIZE_LIMIT (for example 512M). MULTIADMIN_REDISADMIN_BODY_SIZE_LIMIT does the same for Redis imports.

One replica

Sessions and sign-in tickets are held in memory, which keeps logout and single-use tickets exact with no store. Run one replica (with the Recreate strategy on Kubernetes) and expect everyone to sign in again after a restart. Local accounts live in usersFile: keep it on a volume.

How the apps are started

The portal starts each app with node build on a loopback port (3101 for MySQL, 3102 for Redis), with a configuration it writes to a private temporary directory (0600). It polls /api/health, answers 503 while an app is starting, and restarts a crashed app with a backoff of 1 second doubling to 30 seconds. The apps' environment is the portal's minus anything that could move their peer, origin or configuration (ADDRESS_HEADER, ORIGIN, HOST, PORT, BODY_SIZE_LIMIT, MULTIADMIN_*, OIDC_*…); KUBERNETES_SERVICE_* passes through so access checks keep working.

Production checklist

  • Change every secret: cookieSecret (32+ random characters), the apps' own secrets, the bootstrap password.
  • Use real hostnames and TLS, and make sure the ingress sends x-forwarded-proto and x-forwarded-host.
  • Prefer OIDC or an SSO proxy over local accounts for people who are not administrators.
  • Nothing else in the pod. The apps trust the portal's identity headers from the pod's loopback address only. A sidecar you do not trust (a service-mesh proxy, for example) could send them too. If you run one, see the trade-offs in the security model.
  • Keep the users file on a volume and back it up.
  • Watch the logs: the portal logs refused sign-ins and app restarts, and each app logs with its prefix ([myadmin], [redisadmin]).
