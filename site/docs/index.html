Overview

svelteMultiAdmin is one portal in front of svelteMyAdmin and svelteRedisAdmin. People sign in once on the portal, then open MySQL or Redis administration without a second login. Both apps run in the same container, each on its own hostname, and keep their own repositories: they are git submodules pinned to release tags.

How it works

  1. You sign in on the portal: local accounts, OpenID Connect, or an SSO proxy in front of it (authentication).
  2. Access rules turn your user name, groups and email into grants: MySQL yes or no, a Redis role (ro, rw, admin), the Redis servers you may see, and whether you manage users (access rules).
  3. Clicking an app goes through /go/<app>: a 30-second, single-use ticket sets a cookie on that app's own hostname.
  4. The portal proxies every request to the app with trusted identity headers (x-multiadmin-*) that it sets itself, after removing anything of that kind a client sent. The apps listen on loopback only and trust those headers only from there, so they never show a login form (security model).
  5. Each app's user menu has Back to Admin portal.

Grants are recomputed on every request: editing an access rule, regrouping a local user or disabling them applies on the next click, on every host. Logging out on the portal ends the session on all hosts. 

browser ──▶ ingress ──▶ MultiAdmin :3000 ── admin.example.com        portal: login, launcher, user admin
                              │          ── mysql.admin.example.com  ── gate ──▶ 127.0.0.1:3101 svelteMyAdmin
                              │          ── redis.admin.example.com  ── gate ──▶ 127.0.0.1:3102 svelteRedisAdmin
                              └─ starts and supervises both apps

Configuration

multiadmin.json (path in MULTIADMIN_CONFIG) is the only file that knows about all three applications. A sample is in the repository: config.sample.json. 

{
	"publicUrl": "https://admin.example.com", // origin only; every host below must be different
	"cookieSecret": "32+ random characters",
	"sessionTtlSeconds": 28800,
	"auth": { "type": "local", "usersFile": "/data/users.json", "bootstrapAdmin": "admin" },
	"access": [
		{ "match": { "group": "platform-admins" }, "grants": { "myadmin": true, "redisadmin": { "role": "admin" }, "userAdmin": true } },
		{ "match": { "group": "devs" }, "grants": { "redisadmin": { "role": "rw", "servers": ["Dev redis1"] } } },
		{ "match": { "group": "*" }, "grants": { "redisadmin": { "role": "ro" } } }
	],
	"apps": {
		"myadmin": { "publicUrl": "https://mysql.admin.example.com", "config": "/config/myadmin.json" },
		"redisadmin": { "publicUrl": "https://redis.admin.example.com", "config": "/config/redisadmin.json" }
	}
}
Key Meaning
publicUrl The portal's origin (http or https, no path). Also the redirect base for OIDC (<publicUrl>/auth/callback).
cookieSecret At least 32 characters. Signs session cookies and seals the OIDC flow cookie. svelteRedisAdmin's cookie secret is derived from it when its own config does not set one.
sessionTtlSeconds Session lifetime. Default 28800 (8 hours).
auth One of local, oidc, trusted-header. See authentication.
access The rules that grant access. See access rules.
apps.<id>.publicUrl The hostname of the app. Must differ from the portal and from the other app.
apps.<id>.config Path of the app's own configuration (its servers, discovery, audit). Relative paths resolve from the portal config's directory. Omit an app to leave it out of the bundle.
apps.<id>.label Name on the launcher card. Defaults to MySQL / Redis.

The apps' own configuration

myadmin.json and redisadmin.json are the apps' normal configuration files: servers, Kubernetes discovery, audit log. The portal overwrites their authentication keys when it starts each app (their signon and header identity settings, trusted networks, sign-in and logout links, and the Portal back-link), so you never write header names or trusted networks yourself. See the apps' own documentation for everything else: svelteRedisAdmin, svelteMyAdmin.

A svelteMyAdmin server needs an explicit user (and password): with SSO everyone shares that MySQL account. Kubernetes access checks of the app can narrow who may use a server. A server without user makes that app refuse to start, with a message naming it.

Environment variables

Variable Meaning
MULTIADMIN_CONFIG Path of multiadmin.json. Required.
MULTIADMIN_CHILDREN_DIR Where <app>/build live. Default /app/children. For development.
MULTIADMIN_BOOTSTRAP_PASSWORD Password of the first local admin (see authentication).
MULTIADMIN_BOOTSTRAP_GROUPS Groups of that first admin. Default platform-admins.
MULTIADMIN_<APP>_BODY_SIZE_LIMIT Upload limit of one app (MYADMIN or REDISADMIN), passed to it as BODY_SIZE_LIMIT.
PROTOCOL_HEADER, HOST_HEADER How the portal learns its public origin behind an ingress. Set in the image to x-forwarded-proto and x-forwarded-host. See deployment.
PORT, HOST Where the portal listens. Defaults 3000 and 0.0.0.0 in the image.

/api/health answers ok once the portal is up and is meant for liveness and readiness probes.

Interface

The portal looks like the two apps (same components, theme tokens, light, dark and system themes) and speaks English, French and Spanish with the same gettext-style catalogs. The language is remembered in the multiadmin_lang cookie. The apps keep their own language settings.
