Security model

The portal is the only thing a browser talks to. It authenticates the person, decides what they may open, and then speaks to each app in the one language both already understand: identity in trusted request headers, accepted only from a trusted network address.

How identity reaches the apps

  1. Both apps already trust identity headers from a proxy, but only when the request's TCP peer is in a configured list (svelteMyAdmin's signon, svelteRedisAdmin's header plugin). The portal reuses that contract: the apps listen on 127.0.0.1 and trust loopback only.
  2. For every proxied request the portal first deletes any header a client could use to impersonate someone: the x-multiadmin-* headers, upstream x-auth-request-* headers, Forwarded and every X-Forwarded-*, hop-by-hop headers, and its own session cookie. Then it sets the identity from the signed-in person alone.
  3. svelteRedisAdmin always receives a role (its "no role means admin" default is unreachable) and, unless the person may see every server, the list of server positions, possibly empty.
  4. Groups are passed only for OIDC and trusted-header sign-in. A group name with a comma or a control character is dropped, because the apps split the header on commas.
  5. The apps' environment is scrubbed of anything that could move their peer address, origin or configuration, so a variable of the portal can never turn "trusted peer: loopback" into something else.

Why one hostname per app

The apps keep absolute URLs and have no base path, so mounting them under /mysql would need about a hundred edits in each repository, forever. Separate hostnames need none. Cookies are host-only, so the portal's session cookie and each app's cookies never mix.

Moving between hosts

A session cookie of the portal does not exist on an app's hostname. /go/<app> mints a ticket that is signed (HMAC), valid 30 seconds, for one app, and single use; the app host redeems it, sets its own cookie, and redirects. A replayed, expired or wrong-app ticket gets a 403 page, never a redirect loop. Open-redirect return paths fall back to /. Sessions live in one table in the portal, so logging out kills every host's cookie at once and disabling a user stops them on their next click.

Trade-offs

We accept In exchange for
Three hostnames (DNS and Ingress rules) No base-path changes in either app.
Anything else on the pod's loopback (a sidecar proxy) could forge identity to the apps Reusing the contract both apps already ship and test, with no new code in them. The alternative, signed tokens verified by each app, removes this risk and costs a new authentication plugin in each repository: it stays the upgrade path.
In-memory sessions and tickets: one replica, sign in again after a restart Instant logout everywhere and exactly-once tickets with no store.
Proxying through the portal (an extra hop) One process tree, one configuration, no extra component to operate.
All-or-nothing access to svelteMyAdmin Keeping its change limited to the back-link: it connects with one MySQL account per server for everyone, narrowed only by Kubernetes checks.
The portal overwrites the apps' authentication settings One source for header names and trusted networks, and no way to opt an app out of SSO inside the bundle.

What has been verified

  • Unit and integration tests with real child processes, real git repositories and a fake OpenID provider cover grants, tickets, header scrubbing, the gate, the proxy (streaming, redirects, cookies, restarts), local sign-in, OIDC (PKCE, state, nonce, replay), trusted headers, client addresses and bundle:update.
  • A run in a browser against the built apps: sign in once, open each app with no second login, the back-link, a restricted user, forged headers ignored, logout ending every host.
  • Not covered: a real OpenID provider, a real SSO proxy, a service mesh, and the Docker image on a cluster. Test those in your environment.
