Updating the apps

svelteMultiAdmin does not contain the apps' code. vendor/svelteMyAdmin and vendor/svelteRedisAdmin are git submodules of their own repositories, pinned to release tags, so each app keeps its own life and the bundle follows their releases. 

pnpm bundle:update                          # both apps to their newest v* tag
pnpm bundle:update redisadmin --to v0.3.1   # one app, a specific tag (also to go back)
pnpm bundle:update --dry-run                # show what would change
git diff --cached && git commit             # the script only stages

What it does

  • Adds the submodule first if it is not there yet.
  • Fetches the tags and picks the highest semver v* release. Pre-releases and tags like latest are ignored. v0.10.0 is newer than v0.9.0.
  • Checks the tag out, stages the new pin and prints the commits in between.
  • It never commits: review git diff --cached, then commit.
  • It is idempotent: at the requested tag it changes nothing.
  • It refuses a submodule with local changes, an unknown tag, and a repository with no release tag yet (it says so: tag a release first).
  • It warns when the pinned app has no Portal configuration key, which means no back-link to the portal in its menu.
  • One app failing does not stop the other; the command exits non-zero if any failed, so CI can notice.

Releasing

The bundle is only as new as the tags of the apps. Merge the work in an app, tag a release there (v0.1.0), then run pnpm bundle:update in svelteMultiAdmin and commit the new pin. The Dockerfile builds each app from its own lockfile, so the bundle always runs the dependencies that release was tested with.

Cloning the bundle

git clone --recurse-submodules https://github.com/razvn/svelteMultiAdmin.git
# or, in an existing clone:
git submodule update --init
